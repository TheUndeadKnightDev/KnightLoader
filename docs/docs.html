Documentation

KnightLoader docs

Everything you need to install KnightLoader and build mods with it. Applies to KnightLoader v1.x on Unity Mono games (IL2CPP titles are not supported).

Installing

  1. Download the latest KnightLoader-vX.Y.Z.zip from the Releases section.
  2. Copy everything in the zip into your game's folder — the one containing the game's .exe (for Raft: ...\steamapps\common\Raft).
  3. Launch the game normally (Steam is fine).
  4. Confirm it's running: the file KnightLoader\KnightLoader.log appears in the game folder and ends with N mod(s) active.

Your game folder will look like this:

Raft\
  Raft.exe
  winhttp.dll              ← Doorstop bootstrap (loads KnightLoader at startup)
  doorstop_config.ini
  .doorstop_version
  KnightLoader\
    KnightLoader.dll        ← the loader
    0Harmony.dll            ← runtime patching library
    Mono.Cecil.dll
    KnightLoader.log        ← created on first launch
  Mods\
    SampleMod.dll           ← mods go here (one DLL each)

No game files are modified. To disable temporarily, rename winhttp.dll to winhttp.dll.disabled.

Your first mod

A mod is a single .NET class-library DLL dropped into Mods\. You need any C# compiler (Visual Studio, Rider, or the dotnet SDK) and three kinds of references, all taken from your KnightLoader install and your game:

  • KnightLoader\KnightLoader.dll — the mod API
  • KnightLoader\0Harmony.dll — only if you patch game code
  • Game assemblies from <Game>_Data\Managed\ — e.g. UnityEngine.CoreModule.dll, and Assembly-CSharp.dll for the game's own classes

Minimal project file (MyFirstMod.csproj):

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>netstandard2.0</TargetFramework>
    <AssemblyName>MyFirstMod</AssemblyName>
  </PropertyGroup>
  <ItemGroup>
    <Reference Include="KnightLoader">
      <HintPath>C:\...\Raft\KnightLoader\KnightLoader.dll</HintPath>
    </Reference>
    <Reference Include="0Harmony">
      <HintPath>C:\...\Raft\KnightLoader\0Harmony.dll</HintPath>
    </Reference>
    <Reference Include="UnityEngine.CoreModule">
      <HintPath>C:\...\Raft\Raft_Data\Managed\UnityEngine.CoreModule.dll</HintPath>
    </Reference>
  </ItemGroup>
</Project>

And the mod itself (MyFirstMod.cs):

using KnightLoader;

[ModInfo("My First Mod", "1.0.0", "YourName")]
public class MyFirstMod : Mod
{
    public override void OnLoad()
    {
        LogInfo("Hello from My First Mod!");
    }
}

Build with dotnet build -c Release, copy MyFirstMod.dll into Mods\, launch the game, and check KnightLoader.log for your hello.

The mod lifecycle

The loader scans Mods\*.dll at startup, instantiates every class implementing IMod, then drives these callbacks on Unity's main thread. Exceptions in any callback are caught and logged per-mod — one broken mod can't take the others down.

CallbackWhen it runsUse it for
OnLoad()Once, after all mods are discoveredSetup, applying Harmony patches
OnUpdate()Every frame (Unity Update)Input polling, per-frame logic — keep it light
OnGUI()Unity's IMGUI pass (multiple times per frame)Overlays, debug UI
OnUnload()Once, on game quitUnpatching, saving, cleanup

Finding things to patch

Modding is 80% reconnaissance. Before you can change a game's behaviour you need to know its class and method names — and those live inside the game's own assemblies. The workflow:

  1. Open the game's code. Load <Game>_Data\Managed\Assembly-CSharp.dll in a decompiler — ILSpy (free, cross-platform) or dnSpyEx (great for Unity). Everything the game does is in there as readable C#.
  2. Search for the concept. Looking to stop fall damage? Search "Damage". Want to change hunger? Search "Hunger" or "Stat". Decompilers let you full-text search across all types.
  3. Find the method that does the thing and note its exact type name, method name, and parameters — you'll need all three to target an overload precisely.
  4. Reference that assembly in your mod's .csproj (add Assembly-CSharp.dll as a <Reference>) so you can write strongly-typed patches against those classes.

Tip: mods often patch MonoBehaviour lifecycle methods (Awake, Start, Update), property getters (great for "always return max"), and event handlers (OnDeath, OnHit). Getters and small methods are the safest, most stable targets across game updates.

Harmony basics

KnightLoader ships Harmony 2 for rewriting game methods in memory at runtime — no game files touched. Declare patches with attributes and apply them in OnLoad. A real example from the Raft SampleMod — cancelling all player damage:

using HarmonyLib;
using KnightLoader;

[ModInfo("God Mode", "1.0.0")]
public class GodMode : Mod
{
    internal static bool Enabled = true;

    public override void OnLoad()
    {
        Harmony.PatchAll();      // applies every [HarmonyPatch] in this DLL
        LogInfo("Patched.");
    }

    public override void OnUnload()
    {
        Harmony.UnpatchAll(Harmony.Id);
    }
}

// PlayerStats.Damage is a real method in Raft's Assembly-CSharp.dll.
// A prefix returning false skips the original entirely.
[HarmonyPatch(typeof(PlayerStats), nameof(PlayerStats.Damage))]
static class Patch_Damage
{
    static bool Prefix() => !GodMode.Enabled;
}

Prefix runs before the original (return false to skip it), Postfix after it, Transpiler rewrites its IL. See the Harmony documentation for the full patching guide.

Advanced patching

Harmony injects special parameter names into your prefix/postfix. Ask for any you need — order doesn't matter, and you only declare the ones you use:

ParameterWhat it gives you
__instanceThe object the method was called on (typed as the target class). Read/modify its fields.
__resultThe return value. In a postfix, change it to alter what the game sees. Use ref.
ref float amountAn original parameter by name — ref lets you rewrite it before the method runs.
__stateScratch value passed from your prefix to your postfix (e.g. remember a value before, compare after).
___privateFieldThree underscores = access a private field on the instance by name. Read or write it.
// Halve all incoming damage instead of blocking it — edit the argument in place.
[HarmonyPatch(typeof(PlayerStats), nameof(PlayerStats.Damage))]
static class HalfDamage
{
    static void Prefix(ref float damage) => damage *= 0.5f;
}

// Force a getter to always return true (reach a private field with three underscores).
[HarmonyPatch(typeof(Inventory), "get_IsFull")]
static class NeverFull
{
    static void Postfix(ref bool __result) => __result = false;
}

Targeting overloads. When a method name is ambiguous, pass the parameter types to pick the exact one:

[HarmonyPatch(typeof(SomeClass), nameof(SomeClass.Method), new[] { typeof(int), typeof(bool) })]

Patching private methods that nameof can't see — use the string name, or find them with AccessTools:

var target = AccessTools.Method(typeof(SomeClass), "PrivateMethod");
Harmony.Patch(target, prefix: new HarmonyMethod(typeof(MyPatch), nameof(MyPatch.Prefix)));

Worked example: Red Shark

Not every mod patches methods. Sometimes you just manipulate live objects. Our Red Shark mod for Raft recolours every shark — a good example of the "scan & modify" pattern using only OnUpdate, no Harmony at all:

[ModInfo("Red Shark", "1.0.0")]
public class RedShark : Mod
{
    readonly HashSet<int> done = new HashSet<int>();
    float timer;

    public override void OnUpdate()
    {
        // Throttle: scan a couple of times per second, not every frame.
        timer += Time.deltaTime;
        if (timer < 1.5f) return;
        timer = 0f;

        foreach (var smr in Object.FindObjectsOfType<SkinnedMeshRenderer>())
        {
            if (smr == null || done.Contains(smr.GetInstanceID())) continue;
            if (!smr.name.ToLower().Contains("shark")) continue;   // only sharks
            done.Add(smr.GetInstanceID());
            foreach (var m in smr.materials) m.color = Color.red;   // per-instance copy
        }
    }
}

Lessons worth stealing: throttle scene scans (they're not free), remember what you've already touched with a HashSet of instance IDs, and use .materials (per-object copies) rather than .sharedMaterial (which would recolour every object using that material).

How injection works

Under the hood, getting your code to run inside a shipping game is a careful dance:

  1. UnityDoorstop (the winhttp.dll proxy next to the game exe) hijacks the Mono runtime as it initialises and calls KnightLoader's entry point — before any game code runs.
  2. At that instant Unity's engine bindings aren't ready yet. Touching UnityEngine.Debug.Log or creating a GameObject here would permanently break that call for the whole session (Mono compiles the unbound "internal call" as a throw). So the loader does nothing Unity-related yet.
  3. Instead, KnightLoader uses Mono.Cecil to rewrite the game's assemblies in memory, injecting a one-line call into an early startup method (e.g. a MonoBehaviour.Awake). Nothing is written to disk.
  4. When the game naturally runs that method — on the main thread, engine fully alive — our injected call fires, and that's when the loader safely creates its host object and loads your mods.

This is why the loader touches zero files on disk, and why it works across wildly different games. For split-assembly games (like Valheim, whose code lives in assembly_valheim.dll rather than Assembly-CSharp.dll), it patches every game-code assembly, so the bootstrap always fires.

Dependencies & shipping

If your mod uses a library that isn't already in the game (say a JSON parser the game doesn't ship), drop that DLL into the Mods\ folder alongside your mod. KnightLoader's assembly resolver looks there automatically. Don't ship copies of the game's own assemblies or UnityEngine — those are already loaded.

Build against, but don't redistribute, the game's Assembly-CSharp.dll — it's the game's code. Reference it locally; ship only your mod.

Logging & debugging

  • KnightLoader\KnightLoader.log — the loader's log, in the game folder. Your LogInfo/LogWarn/LogError lines land here, prefixed with your mod name. Truncated each launch.
  • The game's Player.log — Unity's own log (Windows: %USERPROFILE%\AppData\LocalLow\<Company>\<Game>\Player.log). KnightLoader mirrors messages here too once the engine is ready, and it captures full stack traces.
  • Exceptions are isolated — if your OnUpdate throws, the loader catches it, logs it, and keeps the other mods running. Check the log for "threw in <your mod>".
  • Iterating: close the game (the DLL is locked while it runs), rebuild, drop the new DLL in Mods\, relaunch. There's no hot-reload yet.

Other Unity games

The loader core contains no Raft-specific code. To use it with another Unity Mono game, copy the same four items (winhttp.dll, doorstop_config.ini, .doorstop_version, KnightLoader\) into that game's folder and create a Mods\ folder. A game is Mono if its install has a MonoBleedingEdge folder; if it has GameAssembly.dll instead, it's IL2CPP and not supported.

Version floor: KnightLoader targets Unity 2017.2 or newer (the "module" era, where UnityEngine.CoreModule.dll exists in Managed\). Unity 5.x / pre-2017 games ship a single monolithic UnityEngine.dll and the older .NET 3.5 Mono profile, which this build can't load.

Distributing your mod

A KnightLoader mod is just a DLL. To share it, zip your YourMod.dll (plus any extra dependency DLLs it needs) and tell users to drop it into their Mods\ folder. That's the whole install. Good practice:

  • Put a [ModInfo("Name", "1.0.0", "You")] on your class so it shows a friendly name in the log.
  • Include a short readme: which game + version it's for, what it does, and any hotkeys.
  • Never bundle the game's Assembly-CSharp.dll or UnityEngine DLLs — only your own code.
  • Version your mod so users know when to update. KnightLoader itself is versioned separately.

FAQ

QuestionAnswer
Will this get me banned?Don't use it on multiplayer games with kernel anti-cheat (EasyAntiCheat / BattlEye). For singleplayer or mod-friendly servers it's fine. KnightLoader never modifies files on disk, but injected code is still detectable by anti-cheat.
Does it work in multiplayer?Cosmetic/client-side mods generally work; anything that changes game state usually needs the host (and other clients) to run the same mod. That's game-specific.
Will a game update break my mods?KnightLoader itself is resilient (it doesn't touch files). Individual mods can break if the game renames the methods they patch — patch stable targets like getters to minimise this.
Is it open source?KnightLoader is free to use. It's built on the open-source UnityDoorstop and Harmony projects.
Can I load multiple mods?Yes — every DLL in Mods\ loads independently. One crashing doesn't affect the others.
IL2CPP games?Not with the stable loader. IL2CPP support is experimental — see the IL2CPP research.

Troubleshooting

SymptomFix
No KnightLoader.log appearsDoorstop didn't load: check winhttp.dll and doorstop_config.ini are next to the game's .exe, and enabled=true in the ini.
Log says No IMod implementation foundYour mod class must be public, non-abstract, and implement IMod (or extend Mod).
Failed to load <mod>.dllUsually a missing reference — ship extra dependency DLLs in Mods\ (the loader resolves from there), and build against the game's own assembly versions.
Legacy Input throwsSome games (incl. Raft) use the new Input System; wrap legacy input in try/catch or use UnityEngine.InputSystem.
Game misbehaves with mods installedRename winhttp.dll → winhttp.dll.disabled to confirm it's mod-related, then remove mod DLLs one at a time.

Uninstalling

Delete winhttp.dll, doorstop_config.ini, .doorstop_version, the KnightLoader\ folder and the Mods\ folder from the game directory. That's everything — no game files were ever changed.
